# Bookmark-X 更新日志

生成简洁、准确、可直接粘贴到 GitHub Release 的中英双语更新日志。

## 核对版本范围

1. 优先使用用户明确指定的目标版本；否则读取 `build.gradle` 中的 `version`。
2. 如果目标版本已有标签，以该标签为比较终点；否则以当前 `HEAD` 为终点。
3. 基准版本使用目标版本之前最近的正式版本标签。用户给出参考 Release 时，该页面主要用于确认文案格式；除非用户明确指定，不要把它当作变更范围。
4. 至少检查以下证据：
   - `git log --oneline --no-merges <基准>..<终点>`
   - `git diff --stat <基准>..<终点>` 和变更文件列表
   - `build.gradle` 中的 `version`、`changeNotes` 与兼容版本范围
   - 与用户可见行为相关的具体代码、资源文件和国际化文本差异

不要只根据提交标题写日志。提交标题含糊、重复或只描述实现时，继续查看差异，确认用户实际能感知的变化。

## 提炼内容

- 只写用户可见的新功能、交互改进、兼容性变化和缺陷修复。
- 合并描述同一功能的多个提交，避免重复条目。
- CI、README、代码重构、测试和内部依赖调整通常不单独列出；当它们直接改变兼容范围、安装结果或用户体验时才写入。
- 准确区分“自动执行”“检测后提示”和“用户手动触发”等行为，不夸大实现。
- 兼容版本没有变化时，不重复上一版本的兼容性说明。
- 中文与英文条目数量、顺序和含义必须一致。英文使用自然的产品发布语气，不逐字硬译。
- 没有足够证据支持的变化不要猜测；必要时明确说明无法确认的部分。

## 输出模板

默认只输出 Release 正文，不额外添加版本标题、分析过程或测试说明：

```markdown
**更新内容 / Changelog**

**中文**

* 中文更新项一
* 中文更新项二

**English**

* English update item one
* English update item two
```

条目应简短具体，通常一句话说明一项用户价值。若用户要求其他格式，以用户指定格式为准。

## 操作边界

生成日志默认是只读任务。只有用户明确要求时，才修改 `build.gradle`、创建 Release、打标签、提交或推送代码。
